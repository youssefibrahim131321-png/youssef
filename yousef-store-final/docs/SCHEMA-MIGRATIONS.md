# هجرات الـ Schema المرقّمة (`store.js` → `MIGRATIONS`)

> ده عن **تعديلات الـ Schema داخل نفس نوع القاعدة (Postgres)** — مختلف عن
> [`MIGRATION.md`](MIGRATION.md) اللي بيتكلم عن نقل بيانات من SQLite لـ Postgres.

## ليه الملف ده موجود

`SCHEMA_SQL` في `store.js` بيبني الجداول الأساسية بـ `CREATE TABLE IF NOT EXISTS`.
ده كويس للتشغيل الأول، لكن أي تعديل لاحق (عمود جديد، تعبئة بيانات قديمة، تغيير
نوع عمود...) لازم يتسجّل كـ **هجرة مرقّمة** بدل ما يتحط جوّه `createStore`
مباشرة بلا تتبّع. كل هجرة بتتسجّل في جدول `schema_migrations` بعد أول نجاح،
وما بتتنفّذش تاني بعد كده.

## إزاي تضيف هجرة جديدة

في `store.js`، دور على `const MIGRATIONS = [...]` وضيف عنصر جديد في آخر
المصفوفة:

```js
{
  id: 3, // (إجباري) رقم تصاعدي جديد — ما تغيّرش أرقام موجودة ولا تعيد استخدامها أبدًا
  name: 'وصف قصير للتعديل',
  run: async (pool) => {
    await ensureColumn(pool, 'products', 'weight_kg', 'NUMERIC');
    // أو أي ALTER/UPDATE تاني — اكتبها idempotent قدر الإمكان زي باقي الهجرات
  }
}
```

قواعد مهمة:

- **الـ `id` لازم يكون تصاعدي وما يتكررش.** هو المفتاح الأساسي في
  `schema_migrations`، فأي تعارض هيرمي خطأ عند الإقلاع.
- **متعدلش هجرة قديمة اتنفّذت فعلًا في أي بيئة إنتاج.** لو محتاج تصحيح، ضيف
  هجرة جديدة برقم أعلى بدل ما تعدّل القديمة.
- الهجرات بتتنفّذ بالترتيب الرقمي مرة واحدة بس لكل قاعدة بيانات (بيتم تسجيلها
  في `schema_migrations`)، فمينفعش تفترض ترتيب تنفيذ تاني أو تنفيذ متكرر.
- استخدم `ensureColumn(pool, table, column, definition)` الموجودة فوق
  للأعمدة الجديدة — بترجع `false` لو العمود موجود بالفعل فمينفعش تكرار.
- لو الهجرة فشلت، الإقلاع بيتوقف (`throw`) بدل ما يكمل بـ Schema ناقص — راجع
  اللوج، اصلح المشكلة، وأعد التشغيل؛ الهجرات اللي قبلها اتسجّلت خلاص فمش
  هتتعاد.
